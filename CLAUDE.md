# ASTROLABE — Agent Operating Manual

ASTROLABE fuses Calyx (Rust association-native DB engine, currently at `vendor/calyx`) with codebase-memory-mcp (C code-graph MCP server, currently at `vendor/codebase-memory-mcp`) into one Rust-host binary (`crates/astrolabe-server`) with the C half linked as `libcbm.a` (`crates/cbm-sys`, `crates/astrolabe-bridge`). **Both parent codebases are ASTROLABE's own first-class source (owner directive, 2026-07-12): pulled in once, owned outright, edited directly, evolved in place on a stable base — this is its own project built from the original code of both repos plus the custom code that connects them. "Vendoring" is dead: no pins, no patch overlays, no upstream-refresh procedure, no upstream-tracking of any kind. The origin repos are at most a read-only quarry to copy useful code from as normal development. EPIC #286 tracks dismantling the residual vendoring machinery (pins/`patches/` overlays/`VENDORED.md`) and relocating the trees out of `vendor/`.** Plan of record: `docs/astrolabe-blueprint.md`. Binding upstream doctrine: `docs/BUILDING_ON_CALYX.md` (the Calyx builder's handbook the blueprint derives from — embed-vs-encode, atoms → all base associations → differentiate → kernel → compose, the anti-pattern list; on conflict the blueprint's code-domain decisions win, recorded there as design corrections). **State of record: GitHub issues — nothing else.**

## The one rule that outranks all others

**GitHub issues are the single source of truth for what is done, in progress, and remaining.** The blueprint describes the *design*; it never records *progress*. If you learn something about project state, it goes in an issue comment. If it isn't on an issue, it didn't happen.

## Execution context (mandatory)

- **Canonical workspace:** all repository work starts from and remains rooted at `C:\code\Astrolabe`. Run commands with that exact directory as the working directory. Do not use a copied checkout, shadow tree, or project-owned output directory outside this workspace.
- **Native Windows build toolchain:** produce build/test evidence with the native Windows GNU toolchain via the launcher, because the Rust host and the static `libcbm.a` archive must share one ABI (see Build notes). Use PowerShell and native Windows executables; run POSIX scripts under a Git for Windows Bash executable (e.g. `C:\Program Files\Git\bin\bash.exe`) for a consistent, pinned toolchain rather than an arbitrary shell.
- **WSL coexistence (do not fight the host):** WSL is a normal, permitted part of this Windows machine. Project scripts, the launcher, and gates MUST NOT treat WSL — its services, packages, distributions, `wsl.exe`, `wslservice`, `vmmemWSL`, or `C:\Windows\System32\bash.exe` — as a fault condition, must never fail closed on its presence, and must never stop, disable, uninstall, or DISM-service it. Do not build anything that wipes, repairs, or polices WSL to keep the host "pure"; a system that deletes the operator's WSL install is a defect, not a safety property. The only reason evidence runs natively is ABI/target match (below), not hostility toward WSL.
- **Native-target evidence:** Astrolabe ships as a native Windows binary, so build/test/gate evidence must be produced by the native Windows toolchain from the canonical workspace — a build for a different target (including a Linux or WSL build) exercises different code paths and does not satisfy a Windows DoD. This is about matching the shipping target, not excluding WSL. A gate that genuinely cannot run natively must be reported and tracked.
- **Windows-only until fully operational (owner directive, 2026-07-11):** ASTROLABE targets **Windows and no other system** until the whole system is operational and built. Do not do cross-platform work now — no Linux/macOS builds, no Linux-host runbooks, no cross-platform goldens, no sanitizer-on-Linux plans, no portability refactors "while we're in here." Porting is a deliberate **final phase**, tracked in the `Port — cross-platform (deferred)` milestone; it is not started, not scheduled early, and not a blocker for any Windows DoD. A DoD clause whose evidence owner is a non-Windows platform is **not** a coverage gap to apologize for and **not** a runbook someone should execute now: it is `DEFERRED[ASTRO_PORT_PHASE]` — labeled, counted, tracked on #238, and **never presented as passing** (invariants 1 and 3 still bind; deferral is disclosed, not silent). An issue may close on native-Windows evidence alone once its non-Windows clauses are re-pointed at the port milestone. Deferral is not abandonment: we intend to port, at the end, once Windows works.
- **Aggregate evidence capture:** invoke aggregate gates through `scripts\\invoke-native-aggregate.ps1` and consume its stdout directly. The wrapper deliberately creates no evidence log. Never wrap it in `Tee-Object`, a transcript, or host-side redirection to a file under `%TEMP%`, an agent scratchpad, or any other path; the invoking process is the evidence stream.
- **Autonomous project decisions:** make and execute the technical, environment/toolchain, prioritization, and implementation choices required to reach ASTROLABE's intended end state. Choose the most robust, durable, project-aligned option rather than a locally easier workaround; do not pause for routine approval or leave a known next step undecided.
- **Fast feedback loops (owner directive, 2026-07-12; state: #262):** designing for fast feedback so we can iterate quickly is a first-class development objective, and it is what an agent optimizes for — get a *correct* pass/fail signal in the **least wall-clock that still proves the change**; slow feedback is a defect to engineer away, not a cost to pay. **Tiered verification, matched to blast radius:** Tier 0 = `cargo check`/`clippy`/`nextest` on the touched crate(s) only (inner loop, warm `target/`, seconds); Tier 1 = the affected crates' full suites + fmt + lints (pre-commit, minutes); Tier 2 = the full native aggregate (`invoke-native-aggregate.ps1`, ~30–60 min) **only** before merging to `main` or when the change's blast radius includes foundational surface — the identity spine (`astrolabe-domain`), the FFI boundary (`cbm-sys`/`astrolabe-bridge`/libcbm), the gate scripts, cross-crate contracts, or the C half. Before choosing a tier, **measure** blast radius with codebase-memory-mcp `trace_path(direction="both")` + `detect_changes(base_branch=main)` and run the *minimum tier whose coverage ⊇ the blast radius*. Do **not** run a 30–60-min aggregate to prove a change a targeted check fully covers — that is the anti-pattern this rule forbids. Keep `target/` **warm within a session's inner loop** (the "contiguous verification batch" carve-out below in "Clean after every use"); the mandatory wipe stays at every boundary (turn/pause/stop/issue-close/handoff) and before release-artifact gates, and the #197 live-PID lock remains inviolable. Fast feedback **never weakens** the HONEST invariants or FSV: closure evidence must still cover the change's real blast radius, read persisted state (FSV byte readback), and label/count every skip or deferral — this is about not paying for coverage you don't need, never skipping coverage you do need. Tooling: `check-fast.sh` (Tier 0) + build-speed config are #263; the flagship Tier-2 speedup is #189 (redundant recompiles); heavy-test tiering is #264.
- **Continuity and state:** GitHub issues and their comments are the durable state record. On every resume or context compaction, re-read `AGENTS.md`, this file, the active issue and all of its comments, and the live Git/worktree state before acting. This is a sole-agent repository: a prior `status:in-progress` claim never prevents continuation.
- **Reality-first closure:** an implementation, test, gate, or workflow is evidence only after direct verification against its real artifact, process, browser state, or persisted data. Record the command, execution context, and result in the issue before closure. After every issue close, commit and push the verified state immediately.
- **Synapse and hygiene:** browser work uses only the already-open authenticated Chrome session through Synapse, opening new background tabs there rather than launching a browser. Keep worktrees, branches, temporary tools, and outputs clean. When work reveals a problem outside the active fix, create a tracked GitHub issue rather than silently carrying it forward; report unavailable Synapse capabilities in `ChrisRoyse/synapse` when that prevents needed verification or control.
- **Workspace-local outputs:** repository-controlled build products, test databases, logs, fixtures, and temporary outputs must stay under `C:\code\Astrolabe`, normally under `target/`, and must never be staged or committed.
- **Clean after every use:** every build, test, or check invocation (or one explicitly identified contiguous verification batch) owns its `target/` output and must delete `C:\code\Astrolabe\target` immediately after evidence is captured, including on failure or interruption. The launcher holds a session lock at `.tmp/astrolabe-launcher.lock` (JSON: pid, started, command); a session may clean `target/` or stop toolchain processes only when that lock is absent or names a dead PID. Never stop or clean another session's live locked run — wait for the lock to release or record the conflict on the active issue. Verify that `target/` is absent before starting unrelated work and before every pause, stop, issue close, turn end, or handoff. Never allow build output to accumulate between sessions.
- **Multi-session lock discipline (#197):** (1) every lock file (launcher session lock, any maintenance lock) names its owner as JSON — PID(s), driving issue, start time. (2) A lock naming any **live** PID is inviolable: never remove it, never stop its processes, never clean `target/` under it. A lock naming only dead PIDs may be cleaned only **after** posting PID-probe evidence to the owning issue. (3) Tracker-comment **before** acquiring or removing any lock, and re-read the driving issue's latest comments before acting on lock state — the tracker is the only shared channel between sessions. (4) Multi-hour gate or servicing runs must be launched detached from any agent tool-call timeout (no foreground tool call may own a multi-hour process tree), with the run's launcher PID posted to the driving issue at start so other sessions verify liveness instead of guessing; this is the operating doctrine for `scripts\invoke-native-aggregate.ps1` long runs. (5) FSV of lock semantics uses isolated fixture roots, never the live shared workspace.
- **No CI/CD — banned (owner directive, 2026-07-11):** GitHub Actions and every other hosted CI/CD system are banned in this repository. Nothing may be written for, configured in, or justified by `.github/` workflows, required status checks, or any CI job — do not create `.github/` content, do not cite a CI job as coverage owner, do not defer evidence "until CI runs." Verification is local full-state verification only: the check scripts, the native aggregate via the launcher, and FSV byte readback, executed from the canonical workspace with output recorded on the issue. The `ci/` directory that remains holds local gate configs consumed by the check scripts — a historical name, not GitHub configuration (#224 tracks scrubbing residual CI-ownership wording and the rename-or-document decision).
- **No host servicing by project tooling:** project scripts and the launcher perform no operating-system servicing — no DISM, no Windows-feature enable/disable, no WSL install or uninstall — and must not fail closed on transient OS-servicing state. Host administration is the operator's concern, outside the build/test loop. (The former exclusive-host-maintenance / WSL-removal machinery has been retired; see the closed WSL-direction issues.)

## Issue workflow (mandatory, in order)

1. **Pick**: choose an issue labeled `status:ready` in the lowest-numbered open milestone (phases must complete in dependency-spine order: `P0 → P1 → P2 → (P3 ∥ P4) → P5 → P6 → (P7 ∥ P8) → P9`; see EPIC #65). Never start a `status:blocked` or `status:needs-spec` issue.
2. **Claim**: comment on the issue: what you're about to do, your plan in ≤5 bullets. Swap label `status:ready` → `status:in-progress`. If the issue already has `status:in-progress` and a claim comment newer than 48h, pick a different issue.
3. **Verify the claim**: re-read the issue body **and all comments** — progress comments record what prior sessions already completed. Never redo checked DoD items; verify them instead (run the named test/gate) and note the result.
4. **Work in scope**: implement ONLY what the issue's Scope section says. Discovered adjacent work = file a new issue with labels + milestone + a `Blocked by:`/`Blocks:` line, and link it in a comment. Never expand scope in place.
5. **Commit discipline**: every commit message body must reference the issue (`Refs #N`, or `Closes #N` on the final commit). No commit may touch `docs/astrolabe-blueprint.md` to record progress — status prose in the blueprint is banned (design corrections are fine).
6. **Prove, then check the box**: a DoD checkbox may only be checked in the same session that ran its verification (test name + result pasted in a comment). Tests must verify persisted state (FSV byte readback), not API echoes.
7. **Gate before done**: select the minimum verification tier whose coverage ⊇ the change's blast radius (see **Fast feedback loops**) — a change confined to non-foundational surface is proven by a targeted Tier 0/1 gate that fully covers it, and that faster gate is the *correct* proof, not a shortcut. The full native-Windows aggregate is required for pre-merge-to-`main` and foundational-surface changes. Run the native-Windows aggregate gate plus the issue's named gates from `C:\code\Astrolabe`. Until a PowerShell aggregate exists, the Bash aggregates (`scripts/check-full.sh`, `scripts/check-release.sh`, and `scripts/check.sh`) may be invoked with a native Git for Windows Bash executable. Paste the command, native execution context, and output tail in the closing comment. `scripts/check-full.sh` bounds the workspace-test phase by default; exit `125` and `DEFERRED[ASTRO_NATIVE_AGGREGATE]` mean downstream suites did not run and are not passing evidence. Use the printed `ASTROLABE_WORKSPACE_TEST_TIMEOUT_SECS=0` continuation only for an intentional full native run. If a gate is unavailable or fails for a pre-existing reason, file/link an issue for it — do not skip silently. In a `finally`/equivalent cleanup path, remove repo-local `target/` and verify it is absent.
8. **Close**: when every DoD box is checked with evidence, close the issue, tick its checkbox in EPIC #65, and move the `status:*` label off. If you must stop early, comment exactly: what's done, what's not, the next concrete step, and any local uncommitted state; swap to `status:ready` if another agent can resume, or `status:blocked` naming the blocker.

## Standing invariants (every PR — the HONEST conjunct; violating these = do not merge)

1. No unlabeled claim — grounded responses carry `trust`, `freshness`, `provenance`.
2. No ungated confidence — refusal with deficit over confident guessing.
3. No silent fallback — every degradation labeled, every skip counted.
4. No constant that could be a measurement — new thresholds/weights are registry-declared knobs or measured values.
5. State verification over green checkmarks — tests read persisted bytes (FSV), assert seeded/worker-count-invariant determinism, pair every mutation with its ledger entry.
6. Production-ready or not merged — no `todo!()`/stubs on shipped paths; fail-closed `{code, message, remediation}` errors; docs on public APIs.

## Build notes

- Toolchain: pinned via `rust-toolchain.toml` (Rust 1.95, edition 2024). The C half needs GNU make + a C toolchain (`cbm-sys/build.rs` respects `MAKE`/`CC`/`CXX`/`AR`).
- Pure-Rust work: `cargo check -p <crate> --all-targets` is fast; full workspace check requires the C toolchain.
- Windows: full native builds use a `x86_64-pc-windows-gnu` Rust host toolchain plus MinGW so Rust and the static libcbm archive share one ABI; the default MSVC host toolchain is not valid for that link. Bootstrap the pinned Rust-CI-compatible GCC 14.1 bundle, LLVM 20.1 analysis bundle, and Cppcheck 2.20.0 source build with `powershell -ExecutionPolicy Bypass -File scripts\windows-gnu-toolchain.ps1 -Bootstrap`; run every native Cargo or aggregate command through that launcher so it selects the matching runtime and pinned lint tools, confines child `TEMP`/`TMP`/`TMPDIR` to a launcher-owned `.tmp` child in the workspace, and removes both that child and `target/` on exit. From native PowerShell, pass child arguments as JSON, for example: `$toolArgs = '["scripts/check-full.sh"]'; .\scripts\windows-gnu-toolchain.ps1 -Command 'C:\Program Files\Git\bin\bash.exe' -CommandArgsJson $toolArgs`. `scripts/check.sh` runs all portable gates before emitting `SKIP[ASTRO_EGRESS_LINUX_REQUIRED]` for the one Linux/strace egress probe; with CI retired that named skip is a recorded coverage gap tracked in #224 (closable by a manual Linux-host run or an explicit permanent-gap record) — never pass evidence. Record unavailable coverage honestly. Never fake a gate result; file/link any coverage gap.
- CBM lint coverage: on non-Linux hosts `scripts/ci-cbm-lint.sh` (historical filename; it is a local gate) emits `SKIP[ASTRO_CBM_CLANG_TIDY_LINUX_REQUIRED]` and still runs the no-skip, cppcheck, clang-format, and NOLINT gates. Its blocking Cppcheck run targets `unix64` and emits `INFO[ASTRO_CBM_CPPCHECK_LINUX_ABI]` for a stable, cross-checkable analyzer ABI. With CI retired, platform-dependent clang-tidy analysis has no CI owner: that named skip is a recorded coverage gap tracked in #224 / #166–#170, closable natively or via a documented Linux-host runbook — never a local analyzer pass. (Its format stage historically validated the hash-checked `patches/cbm` overlay; under #286 the overlays are absorbed into the owned sources and the stage validates those directly.)
- Native formatter: use `python scripts/native-cargo-fmt.py --all -- --check` for the complete workspace and its local path dependencies. Bare `cargo fmt --all` cannot run this graph on Windows because upstream cargo-fmt creates one command line beyond the OS limit; the checked-in runner preserves Cargo's target traversal and invokes rustfmt in bounded batches.
- Target hygiene: local cargo/build/test/check commands may create or grow `./target`. Treat it as disposable evidence workspace, not persistent state. `scripts/check.sh`, `scripts/check-full.sh`, and `scripts/check-release.sh` clean it on direct exit; nested gates delegate cleanup to their direct parent so release artifacts survive only for that same contiguous gate. Delete `./target` immediately after each command or contiguous verification batch, whether it passes, fails, or is interrupted, and verify it is absent. Also verify absence before issue close, turn end, pause, stop, or handoff. If cleanup is blocked by a live process, stop the process if it is yours or file/link an issue with the exact blocker; never leave repo-local build artifacts to accumulate.
