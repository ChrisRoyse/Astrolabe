# ASTROLABE — Agent Operating Manual

ASTROLABE fuses Calyx (Rust association-native DB engine, at `calyx/`) with codebase-memory-mcp (C code-graph MCP server, at `cbm/`) into one Rust-host binary (`crates/astrolabe-server`) with the C half linked as `libcbm.a` (`crates/cbm-sys`, `crates/astrolabe-bridge`). **Both parent codebases are ASTROLABE's own first-class source (owner directive, 2026-07-12): pulled in once, owned outright, edited directly, evolved in place on a stable base — this is its own project built from the original code of both repos plus the custom code that connects them. "Vendoring" is dead: no pins, no patch overlays, no upstream-refresh procedure, no upstream-tracking of any kind. The origin repos are at most a read-only quarry to copy useful code from as normal development. EPIC #286 dismantled the residual vendoring machinery (pins/patch overlays/`VENDORED.md`) and relocated the trees out of `vendor/` to top-level `calyx/` and `cbm/` (Phase B).** Plan of record: `docs/astrolabe-blueprint.md`. Binding upstream doctrine: `docs/BUILDING_ON_CALYX.md` (the Calyx builder's handbook the blueprint derives from — embed-vs-encode, atoms → all base associations → differentiate → kernel → compose, the anti-pattern list; on conflict the blueprint's code-domain decisions win, recorded there as design corrections). **State of record: GitHub issues — nothing else.**

## The one rule that outranks all others

**GitHub issues are the single source of truth for what is done, in progress, and remaining.** The blueprint describes the *design*; it never records *progress*. If you learn something about project state, it goes in an issue comment. If it isn't on an issue, it didn't happen.

## Execution context (mandatory)

- **Canonical workspace:** all repository work starts from and remains rooted at `C:\code\Astrolabe`. Run commands with that exact directory as the working directory. Do not use a copied checkout, shadow tree, or project-owned output directory outside this workspace.
- **Native Windows build toolchain:** produce build/test evidence with the native Windows GNU toolchain via the launcher, because the Rust host and the static `libcbm.a` archive must share one ABI (see Build notes). Use PowerShell and native Windows executables; run POSIX scripts under a Git for Windows Bash executable (e.g. `C:\Program Files\Git\bin\bash.exe`) for a consistent, pinned toolchain rather than an arbitrary shell.
- **WSL coexistence (do not fight the host):** WSL is a normal, permitted part of this Windows machine. Project scripts, the launcher, and gates MUST NOT treat WSL — its services, packages, distributions, `wsl.exe`, `wslservice`, `vmmemWSL`, or `C:\Windows\System32\bash.exe` — as a fault condition, must never fail closed on its presence, and must never stop, disable, uninstall, or DISM-service it. Do not build anything that wipes, repairs, or polices WSL to keep the host "pure"; a system that deletes the operator's WSL install is a defect, not a safety property. The only reason evidence runs natively is ABI/target match (below), not hostility toward WSL.
- **Native-target evidence:** Astrolabe ships as a native Windows binary, so build/test/gate evidence must be produced by the native Windows toolchain from the canonical workspace — a build for a different target (including a Linux or WSL build) exercises different code paths and does not satisfy a Windows DoD. This is about matching the shipping target, not excluding WSL. A gate that genuinely cannot run natively must be reported and tracked.
- **Windows-only until fully operational (owner directive, 2026-07-11):** ASTROLABE targets **Windows and no other system** until the whole system is operational and built. Do not do cross-platform work now — no Linux/macOS builds, no Linux-host runbooks, no cross-platform goldens, no sanitizer-on-Linux plans, no portability refactors "while we're in here." Porting is a deliberate **final phase**, tracked in the `Port — cross-platform (deferred)` milestone; it is not started, not scheduled early, and not a blocker for any Windows DoD. A DoD clause whose evidence owner is a non-Windows platform is **not** a coverage gap to apologize for and **not** a runbook someone should execute now: it is `DEFERRED[ASTRO_PORT_PHASE]` — labeled, counted, tracked on #238, and **never presented as passing** (invariants 1 and 3 still bind; deferral is disclosed, not silent). An issue may close on native-Windows evidence alone once its non-Windows clauses are re-pointed at the port milestone. Deferral is not abandonment: we intend to port, at the end, once Windows works.
- **Autonomous project decisions:** make and execute the technical, environment/toolchain, prioritization, and implementation choices required to reach ASTROLABE's intended end state. Choose the most robust, durable, project-aligned option rather than a locally easier workaround; do not pause for routine approval or leave a known next step undecided.
- **FSV-only verification (owner directive, 2026-07-13; supersedes the 2026-07-12 test-doctrine and tiered-gate directives):** the aggregate gate suite, check scripts, gate configs, suite-impact machinery, and gate self-tests are **retired and deleted** — test suites of that kind are judged a waste of wall-clock and are not to be rebuilt. **Full State Verification against reality is the only verification doctrine:** build the real artifact, exercise the real behavior (real data, real stores, never mocks), then **independently read back the persisted state** (bytes on disk, DB rows, process output, registry/ledger entries) and compare it to the claim; probe the relevant edge cases the same way. Evidence = the command, the execution context, and the read-back state, recorded on the driving issue. `cargo build`/`cargo check` proving the artifact compiles, plus a direct FSV of the changed behavior, is the closure bar.
- **Manual FSV only — ALL tests deleted (owner directive, 2026-07-14; supersedes the 2026-07-13 directive's test-tolerance):** passing tests prove **nothing** — "not a single thing can be determined as working if it passes a test; only manual full state verification of reality is this check." Every test was deleted from the tree: all `#[cfg(test)]` modules, all `tests/` directories (crates, `calyx/`, the cbm C suite), trybuild suites, and test scripts. **Never write, run, or cite a test again — for verification, evidence, measurement, or closure.** Verification is done by hand: build the real artifact natively, exercise it yourself with real calls against a real codebase (this repo's own trees are an always-available corpus), independently read back the persisted state (bytes on disk, DB rows, process output, ledger entries) and compare it to the claim; probe edge cases the same way. Measurements (latency, recall, convergence) are taken against the real running binary/server — never via a test harness. `cargo check`/`cargo build` remain valid as artifact-buildability evidence; they are builds, not tests.
- **Batch verification (owner directive, 2026-07-15):** consolidate, never repeat — one native build serves all pending close-gates of a session/wave; orchestrator readback probes for multiple issues run as one combined script in one pass; GitHub mutations (claims, evidence comments, closes) are batched per round; workers/lanes preserve built binaries + fixtures + drivers to the session scratchpad so verification re-runs artifacts instead of rebuilding them. Reuse proven FSV drivers from the scratchpad and prior-issue comments before writing new ones.
- **Continuity and state:** GitHub issues and their comments are the durable state record. On every resume or context compaction, re-read `AGENTS.md`, this file, the active issue and all of its comments, and the live Git/worktree state before acting. This is a sole-agent repository: a prior `status:in-progress` claim never prevents continuation.
- **Reality-first closure:** an implementation, test, gate, or workflow is evidence only after direct verification against its real artifact, process, browser state, or persisted data. Record the command, execution context, and result in the issue before closure. After every issue close, commit and push the verified state immediately.
- **Frozen tree during evidence builds (#424):** the checkout being built — canonical workspace or worktree — must be frozen from the moment an evidence build starts (any build whose artifact will be exercised for FSV) until that artifact's FSV readback is captured. Any edit to that checkout inside the window voids the evidence and requires a rebuild; a build that "happened to win the race" against a mid-build edit is not evidence. FSV evidence records binary-vs-tree provenance: the commit SHA of the built tree and a hash of the produced artifact, recorded together on the driving issue, so every readback is attributable to an exact tree.
- **Synapse and hygiene:** browser work uses only the already-open authenticated Chrome session through Synapse, opening new background tabs there rather than launching a browser. Keep worktrees, branches, temporary tools, and outputs clean. When work reveals a problem outside the active fix, create a tracked GitHub issue rather than silently carrying it forward; report unavailable Synapse capabilities in `ChrisRoyse/synapse` when that prevents needed verification or control.
- **Workspace-local outputs:** repository-controlled build products, test databases, logs, fixtures, and temporary outputs must stay under `C:\code\Astrolabe`, normally under `target/`, and must never be staged or committed.
- **Clean after every use:** every build, test, or check invocation (or one explicitly identified contiguous verification batch) owns its `target/` output and must delete `C:\code\Astrolabe\target` immediately after evidence is captured, including on failure or interruption. The launcher holds a session lock at `.tmp/astrolabe-launcher.lock` (JSON: pid, started, command); a session may clean `target/` or stop toolchain processes only when that lock is absent or names a dead PID. Never stop or clean another session's live locked run — wait for the lock to release or record the conflict on the active issue. Verify that `target/` is absent before starting unrelated work and before every pause, stop, issue close, turn end, or handoff. Never allow build output to accumulate between sessions.
- **Immutable native FSV artifacts (#596):** a native binary that will be exercised after Cargo output is cleaned must be promoted from launcher-owned `target/` during the same issue-owned launcher process with `scripts\native-fsv-artifact.ps1 -Operation Stage`. Execute only the resulting content-addressed artifact through `scripts\native-fsv-run.ps1` while that launcher lease remains live; the runner denies artifact/application-directory deletion, publishes all owner PIDs, and persists artifact/output/tree readback. Independently run `-Operation Inspect`, capture the run record, then use `-Operation Cleanup` only after every recorded PID is proven dead. Direct closure FSV from disposable `target/` is invalid.
- **Multi-session lock discipline (#197):** (1) every lock file (launcher session lock, any maintenance lock) names its owner as JSON — PID(s), driving issue, start time. (2) A lock naming any **live** PID is inviolable: never remove it, never stop its processes, never clean `target/` under it. A lock naming only dead PIDs may be cleaned only **after** posting PID-probe evidence to the owning issue. (3) Tracker-comment **before** acquiring or removing any lock, and re-read the driving issue's latest comments before acting on lock state — the tracker is the only shared channel between sessions. (4) Multi-hour build or servicing runs must be launched detached from any agent tool-call timeout (no foreground tool call may own a multi-hour process tree), with the run's launcher PID posted to the driving issue at start so other sessions verify liveness instead of guessing. (5) FSV of lock semantics uses isolated fixture roots, never the live shared workspace.
- **No CI/CD — banned (owner directive, 2026-07-11):** GitHub Actions and every other hosted CI/CD system are banned in this repository. Nothing may be written for, configured in, or justified by `.github/` workflows, required status checks, or any CI job — do not create `.github/` content, do not cite a CI job as coverage owner, do not defer evidence "until CI runs." Verification is local Full State Verification only, executed from the canonical workspace with output recorded on the issue.
- **No host servicing by project tooling:** project scripts and the launcher perform no operating-system servicing — no DISM, no Windows-feature enable/disable, no WSL install or uninstall — and must not fail closed on transient OS-servicing state. Host administration is the operator's concern, outside the build/test loop. (The former exclusive-host-maintenance / WSL-removal machinery has been retired; see the closed WSL-direction issues.)

## Issue workflow (mandatory, in order)

1. **Pick**: choose an issue labeled `status:ready` in the lowest-numbered open milestone (phases must complete in dependency-spine order: `P0 → P1 → P2 → (P3 ∥ P4) → P5 → P6 → (P7 ∥ P8) → P9`; see EPIC #65). Never start a `status:blocked` or `status:needs-spec` issue.
2. **Claim**: comment on the issue: what you're about to do, your plan in ≤5 bullets. Swap label `status:ready` → `status:in-progress`. If the issue already has `status:in-progress` and a claim comment newer than 48h, pick a different issue.
3. **Verify the claim**: re-read the issue body **and all comments** — progress comments record what prior sessions already completed. Never redo checked DoD items; verify them instead (re-run the named manual FSV against the real artifact) and note the result.
4. **Work in scope**: implement ONLY what the issue's Scope section says. Discovered adjacent work = file a new issue with labels + milestone + a `Blocked by:`/`Blocks:` line, and link it in a comment. Never expand scope in place.
5. **Commit discipline**: every commit message body must reference the issue (`Refs #N`, or `Closes #N` on the final commit). No commit may touch `docs/astrolabe-blueprint.md` to record progress — status prose in the blueprint is banned (design corrections are fine).
6. **Prove, then check the box**: a DoD checkbox may only be checked in the same session that ran its verification (command + result pasted in a comment). Verification is FSV: persisted-state readback, not API echoes.
7. **FSV before done**: build the real artifact natively, exercise the changed behavior against real data, and independently read back the persisted state that proves it (see **FSV-only verification**). Paste the command, native execution context, and read-back evidence in the closing comment. If a needed verification genuinely cannot run, file/link an issue for the gap — never skip silently. In a `finally`/equivalent cleanup path, remove repo-local `target/` and verify it is absent.
8. **Close**: when every DoD box is checked with evidence, close the issue, tick its checkbox in EPIC #65, and move the `status:*` label off. If you must stop early, comment exactly: what's done, what's not, the next concrete step, and any local uncommitted state; swap to `status:ready` if another agent can resume, or `status:blocked` naming the blocker.

## Standing invariants (every PR — the HONEST conjunct; violating these = do not merge)

1. No unlabeled claim — grounded responses carry `trust`, `freshness`, `provenance`.
2. No ungated confidence — refusal with deficit over confident guessing.
3. No silent fallback — every degradation labeled, every skip counted.
4. No constant that could be a measurement — new thresholds/weights are registry-declared knobs or measured values.
5. State verification over green checkmarks — manual FSV reads persisted bytes (never a test's green output), determinism is proven by repeated real runs compared byte-for-byte, and every mutation is paired with its ledger entry read back from the store.
6. Production-ready or not merged — no `todo!()`/stubs on shipped paths; fail-closed `{code, message, remediation}` errors; docs on public APIs.

## Build notes

- Toolchain: pinned via `rust-toolchain.toml` (Rust 1.95, edition 2024). The C half needs GNU make + a C toolchain (`cbm-sys/build.rs` respects `MAKE`/`CC`/`CXX`/`AR`).
- Pure-Rust work: `cargo check -p <crate> --all-targets` is fast; full workspace check requires the C toolchain.
- Windows: full native builds use a `x86_64-pc-windows-gnu` Rust host toolchain plus MinGW so Rust and the static libcbm archive share one ABI; the default MSVC host toolchain is not valid for that link. Bootstrap the pinned Rust-CI-compatible GCC 14.1 bundle, LLVM 20.1 analysis bundle, and Cppcheck 2.20.0 source build with `powershell -ExecutionPolicy Bypass -File scripts\windows-gnu-toolchain.ps1 -Issue <driving-issue> -Bootstrap`; run every native Cargo command through that launcher with the positive driving issue so the matching runtime and pinned lint tools are selected and the launcher lock records its tracker owner. It confines child `TEMP`/`TMP`/`TMPDIR` to a launcher-owned `.tmp` child in the workspace and removes both that child and `target/` on exit. From native PowerShell, pass child arguments as JSON, for example: `$toolArgs = '["build", "--workspace"]'; .\scripts\windows-gnu-toolchain.ps1 -Issue <driving-issue> -Command 'cargo' -CommandArgsJson $toolArgs`. Record unavailable coverage honestly. Never fake a verification result; file/link any coverage gap.
- Worktree layout for wave provisioning (#226/#436): the launcher accepts a build root only from the canonical workspace `C:\code\Astrolabe` or a registered git worktree parked directly under `C:\code\Astrolabe\.claude\worktrees\<name>` (each keeps its own `target/`, `.tmp/`, and session lock, and shares the canonical pinned `.toolchains`/`.sccache`). Provision parallel-session worktrees there (`git worktree add .claude\worktrees\<name> ...`); a registered worktree anywhere else is refused with a structured `LAUNCHER_BOUNDARY[ASTRO_LAUNCHER_ROOT_UNSUPPORTED]` error carrying the `git worktree move` remediation. `-Bootstrap` stays canonical-only.
- Native formatter: use `python scripts/native-cargo-fmt.py --all -- --check` for the complete workspace and its local path dependencies. Bare `cargo fmt --all` cannot run this graph on Windows because upstream cargo-fmt creates one command line beyond the OS limit; the checked-in runner preserves Cargo's target traversal and invokes rustfmt in bounded batches.
- Target hygiene: local cargo/build/check commands may create or grow `./target`. Treat it as disposable evidence workspace, not persistent state. Delete `./target` immediately after each command or contiguous verification batch, whether it passes, fails, or is interrupted, and verify it is absent. Also verify absence before issue close, turn end, pause, stop, or handoff. If cleanup is blocked by a live process, stop the process if it is yours or file/link an issue with the exact blocker; never leave repo-local build artifacts to accumulate.
