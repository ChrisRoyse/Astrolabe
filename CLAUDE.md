# ASTROLABE — Agent Operating Manual

ASTROLABE fuses Calyx (Rust association-native DB engine, at `calyx/`) with codebase-memory-mcp (C code-graph MCP server, at `cbm/`) into one Rust-host binary (`crates/astrolabe-server`) with the C half linked as `libcbm.a` (`crates/cbm-sys`, `crates/astrolabe-bridge`). **Both parent codebases are ASTROLABE's own first-class source (owner directive, 2026-07-12): pulled in once, owned outright, edited directly, evolved in place on a stable base — this is its own project built from the original code of both repos plus the custom code that connects them. "Vendoring" is dead: no pins, no patch overlays, no upstream-refresh procedure, no upstream-tracking of any kind. The origin repos are at most a read-only quarry to copy useful code from as normal development. EPIC #286 dismantled the residual vendoring machinery (pins/patch overlays/`VENDORED.md`) and relocated the trees out of `vendor/` to top-level `calyx/` and `cbm/` (Phase B).** Plan of record: `docs/astrolabe-blueprint.md`. Binding upstream doctrine: `docs/BUILDING_ON_CALYX.md` (the Calyx builder's handbook the blueprint derives from — embed-vs-encode, atoms → all base associations → differentiate → kernel → compose, the anti-pattern list; on conflict the blueprint's code-domain decisions win, recorded there as design corrections). **State of record: GitHub issues — nothing else.**

## The one rule that outranks all others

**GitHub issues are the single source of truth for what is done, in progress, and remaining.** The blueprint describes the *design*; it never records *progress*. If you learn something about project state, it goes in an issue comment. If it isn't on an issue, it didn't happen.

Choose the most robust, durable, project-aligned option rather than a locally easier workaround; do not pause for routine approval or leave a known next step undecided.
- **FSV-only verification (owner directive, 2026-07-13):** the aggregate gate suite, check scripts, gate configs, suite-impact machinery, and gate self-tests are **retired and deleted** — test suites of that kind are judged a waste of wall-clock and are not to be rebuilt. **Full State Verification against reality is the only verification doctrine:** build the real artifact, exercise the real behavior (real data, real stores, never mocks), then **independently read back the persisted state** (bytes on disk, DB rows, process output, registry/ledger entries) and compare it to the claim; probe the relevant edge cases the same way. Evidence = the command, the execution context, and the read-back state, recorded on the driving issue. `cargo build`/`cargo check` proving the artifact compiles, plus a direct FSV of the changed behavior, is the closure bar.
- **Manual FSV only — ALL tests deleted (owner directive, 2026-07-14):** passing tests prove **nothing** — "not a single thing can be determined as working if it passes a test; only manual full state verification of reality is this check." Every test was deleted from the tree: all `#[cfg(test)]` modules, all `tests/` directories (crates, `calyx/`, the cbm C suite), trybuild suites, and test scripts. **Never write, run, or cite a test again — for verification, evidence, measurement, or closure.** Verification is done by hand: build the real artifact natively, exercise it yourself with real calls against a real codebase (this repo's own trees are an always-available corpus), independently read back the persisted state (bytes on disk, DB rows, process output, ledger entries) and compare it to the claim; probe edge cases the same way. Measurements (latency, recall, convergence) are taken against the real running binary/server — never via a test harness. `cargo check`/`cargo build` remain valid as artifact-buildability evidence; they are builds, not tests.
- **Smallest sufficient corpus:** when designing an FSV, ask what is the *least* data that would still prove the behavior completely, and use that. A synthetic fixture whose expected output you can state in advance (known symbols, known call edges, known counts) is stronger evidence than a large real corpus whose correct answer you cannot independently state. Scale up only when the property under test genuinely requires scale.
- **Batch verification (owner directive, 2026-07-15):** consolidate, never repeat — one native build serves all pending close-gates of a session/wave; readback probes for multiple issues run as one combined script in one pass; GitHub mutations (claims, evidence comments, closes) are batched per round. Reuse proven FSV drivers from prior-issue comments before writing new ones.
- **Continuity and state:** GitHub issues and their comments are the durable state record. On every resume or context compaction, re-read `AGENTS.md`, this file, the active issue and all of its comments, and the live Git state before acting. This is a sole-agent repository: a prior `status:in-progress` claim never prevents continuation.
- **Reality-first closure:** an implementation or workflow is evidence only after direct verification against its real artifact, process, browser state, or persisted data. Record the command, execution context, and result in the issue before closure.

FSV evidence records binary-vs-tree provenance: the commit SHA of the built tree and a hash of the produced artifact, recorded together on the driving issue.

## Issue workflow (mandatory, in order)

1. **Pick**: choose an issue labeled `status:ready` in the lowest-numbered open milestone (phases must complete in dependency-spine order: `P0 → P1 → P2 → (P3 ∥ P4) → P5 → P6 → (P7 ∥ P8) → P9`; see EPIC #65). Never start a `status:blocked` or `status:needs-spec` issue.
2. **Claim**: comment on the issue: what you're about to do, your plan in ≤5 bullets. Swap label `status:ready` → `status:in-progress`. If the issue already has `status:in-progress` and a claim comment newer than 48h, pick a different issue.
3. **Verify the claim**: re-read the issue body **and all comments** — progress comments record what prior sessions already completed. Never redo checked DoD items; verify them instead (re-run the named manual FSV against the real artifact) and note the result.
4. **Work in scope**: implement ONLY what the issue's Scope section says. Discovered adjacent work = file a new issue with labels + milestone + a `Blocked by:`/`Blocks:` line, and link it in a comment. Never expand scope in place.
5. **Commit discipline**: every commit message body must reference the issue (`Refs #N`, or `Closes #N` on the final commit). Commit directly to `main`. No commit may touch `docs/astrolabe-blueprint.md` to record progress — status prose in the blueprint is banned (design corrections are fine).
6. **Prove, then check the box**: a DoD checkbox may only be checked in the same session that ran its verification (command + result pasted in a comment). Verification is FSV: persisted-state readback, not API echoes.
7. **FSV before done**: build the real artifact natively, exercise the changed behavior against real data, and independently read back the persisted state that proves it (see **FSV-only verification**). Paste the command, native execution context, and read-back evidence in the closing comment. If a needed verification genuinely cannot run, file/link an issue for the gap — never skip silently. Remove `target/` after evidence is captured and independently verify absence.
8. **Close**: when every DoD box is checked with evidence, close the issue, tick its checkbox in EPIC #65, and move the `status:*` label off. If you must stop early, comment exactly: what's done, what's not, the next concrete step, and any local uncommitted state; swap to `status:ready` if another agent can resume, or `status:blocked` naming the blocker.

## Standing invariants (every PR — the HONEST conjunct; violating these = do not merge)

1. No unlabeled claim — grounded responses carry `trust`, `freshness`, `provenance`.
2. No ungated confidence — refusal with deficit over confident guessing.
3. No silent fallback — every degradation labeled, every skip counted.
4. No constant that could be a measurement — new thresholds/weights are registry-declared knobs or measured values.
5. State verification over green checkmarks — manual FSV reads persisted bytes (never a test's green output), determinism is proven by repeated real runs compared byte-for-byte, and every mutation is paired with its ledger entry read back from the store.
6. Production-ready or not merged — no `todo!()`/stubs on shipped paths; fail-closed `{code, message, remediation}` errors; docs on public APIs.

## Build notes

- Toolchain: pinned via `rust-toolchain.toml` (Rust 1.95, edition 2024), host `aarch64-apple-darwin`. The C half needs GNU make + Xcode Command Line Tools clang (`cbm-sys/build.rs` respects `MAKE`/`CC`/`CXX`/`AR`) and libclang for bindgen.
- Full native build, run directly from the canonical workspace — there is no launcher and no wrapper:
  ```sh
  cargo build --release -p astrolabe-server
  ```
  Pure-Rust work: `cargo check -p <crate>` is fast; a full workspace check requires the C toolchain because `cbm-sys` builds `libcbm.a`.
- `cbm-sys` bindings are **committed per target** (`src/bindings_macos.rs`, `src/bindings.rs`): clang and MSVC disagree on the underlying type of an unsigned C enum, so the bindings cannot be shared across hosts. Regenerate the macOS bindings only when the C headers change, and commit the result.
- **GPU is Metal on Apple Silicon only (owner directive, 2026-08-02).** This machine has an M5 GPU; **no CUDA and no Windows/x86 GPU stack is run, targeted, or supported.** The CUDA tree (`calyx-forge/src/cuda/`), its ONNX Runtime CUDA pinning, and the `ort-cuda13.3-windows-x86_64` lock are **dead weight pending removal**, not doctrine — never extend them and never gate work on them. They are only still present because `pub mod cuda;` at `calyx-forge/src/lib.rs:13` is ungated, which is what makes the lock file a compile-time input on this host (see the `scripts/` note below); gating or deleting that module frees the lock file too.
- GPU: the Forge Metal backend (`calyx/crates/calyx-forge/src/metal/`) is the Apple Silicon path, behind the opt-in `metal` feature. It is **never substituted automatically** — GPU reductions accumulate in tree order, so a vault written with Metal will not byte-match one written with the CPU backend. Backend choice is a decision about the artifact. Metal wins decisively on compute-bound GEMM and loses on bandwidth-bound distance kernels (unified memory already gives the CPU full bandwidth); choose per operation, not per device.
- Formatter: `cargo fmt --all` runs normally on macOS. (A Python wrapper formerly existed only to work around a Windows command-line length limit; it was deleted with the rest of the Windows harness.)
- `scripts/` retains exactly one thing: `toolchains/ort-cuda13.3-windows-x86_64.lock.json`. It is **not** a script — it is a compile-time build input on **every** host including this one, so **do not delete it** despite the `windows` in its name. Two modules `include_bytes!` it: `calyx-forge/src/cuda/runtime_bundle.rs` and `calyx-onnx-runtime/src/windows.rs`. Only the second is cfg-gated (`#[cfg(all(feature = "runtime", windows))]` at `calyx-onnx-runtime/src/lib.rs:8`) and so never compiles here; the binding constraint is `runtime_bundle.rs`, reached through an **ungated** `pub mod cuda;` at `calyx-forge/src/lib.rs:13`. (Corrected 2026-08-02: this note previously named `windows.rs` as the ungated consumer, which is the one path that does *not* apply on macOS.)
- After a build: promote the binary you intend to exercise out of `target/`, capture FSV evidence, then `rm -rf target/` and verify absence. Never leave it on disk.
- **Promote by atomic rename — never `cp` over a live binary path (Apple Silicon).** Every arm64 binary must carry a valid code signature (cargo's linker applies an ad-hoc one), and macOS caches signature validation **per inode**. `cp` writes new bytes into the *existing* inode; if any running process has that inode mapped, the cached signature no longer matches its pages and the kernel kills it with `SIGKILL (Code Signature Invalid)` / `CODESIGNING: Taskgated Invalid Signature`. Write a new inode and `mv -f` it over, which swaps the directory entry and leaves the old inode intact for running processes. Then verify with `codesign -v <path>` and one real invocation. A freshly promoted binary exiting **137** (128+9) is this bug, not a fault in the program. This is the single most likely way to break a running MCP server on this host.
