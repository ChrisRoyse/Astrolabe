# Astrolabe Agent Context

`CLAUDE.md` is the repository operating manual and must be read before doing any work. GitHub issues are the state of record.

The execution boundary is non-negotiable:

- Work only from the canonical checkout at `C:\code\Astrolabe`.
- Produce build/test evidence with native Windows processes and the native GNU toolchain, because the Rust host and the static `libcbm.a` archive must share one ABI. Run POSIX scripts under a Git for Windows Bash executable (e.g. `C:\Program Files\Git\bin\bash.exe`) for a consistent, pinned toolchain.
- WSL coexistence: WSL is a normal, permitted part of this Windows machine. Project scripts, the launcher, and gates must never treat WSL (services, packages, distributions, `wsl.exe`, `wslservice`, `vmmemWSL`, `C:\Windows\System32\bash.exe`) as a fault condition, must never fail closed on its presence, and must never stop, disable, uninstall, or DISM-service it. Do not build anything that wipes or polices WSL to keep the host "pure." Evidence runs natively only to match the shipping target, not out of hostility toward WSL.
- Native evidence requirement: a build for a different target (including a Linux or WSL build) exercises different code paths and does not satisfy a Windows DoD; re-run required evidence natively and record the Windows execution context in the issue. A verification that genuinely cannot run natively is a coverage gap to file, not a host to modify.
- Run native Cargo and C build commands through `scripts\\windows-gnu-toolchain.ps1`; it pins the matching GNU runtime and LLVM analysis tools, confines temporary files to a launcher-owned workspace child, and removes that child and `target/` on normal exact-owner exit. If attributed children remain live or their state is unevaluable, the launcher preserves the entire owned state and exits with a cleanup error. It holds a fail-closed schema-v2 lease at `.tmp/astrolabe-launcher.lock`; ownership is the exact Windows process identity `(pid, owner_process_start_utc_ticks)`, never a numeric PID alone. Only the authoritative classifier's `absent` state permits a new claim. `held`, stale/PID-reused, unreadable, interrupted-transition, and process-query-fault states never authorize ordinary deletion or target cleanup.
- Multi-session lock discipline (#197/#611/#617): claim, exact-owner cleanup, and explicit reclaim serialize across Windows sessions through one `Global\` mutex derived from the opened launcher root's filesystem identity. A matching live process identity is inviolable (never remove its state, stop its process, or clean `target/` under it). Every v2 lease binds an exact attribution manifest, generation-specific TEMP directory, and deterministic non-breakaway `Global\` Job Object; an observed or unevaluable Job is preserving even when its member list is empty. Stale v2 or transition-bound partial state is archived only after re-reading the owning issue, posting exact PID + creation-ticks + path/hash probe evidence, and using `scripts\\reclaim-launcher-lock.ps1`, which independently verifies the `gh` comment, probes owner/Job twice, and reads back durable authorization/finalization/completion/archive bytes. Fresh pre-v2 or owner-unreadable state without deterministic Job derivation is permanently preserving; legacy/quarantine switches only resume an already-published strictly linked marker or quarantine an exact malformed subordinate stage under a valid modern transition. Tracker-comment before acquiring or removing any lock and re-read the driving issue first; launch multi-hour runs detached from tool-call timeouts with the full launcher identity posted at start; lock FSV uses isolated fixture roots only.
- Frozen Git mutation boundary (#519): while an exact launcher lease is live, the dedicated owner retains the operating worktree's Git `index.lock` as a write-through, delete-on-process-exit interlock and holds deny-write/delete handles over every tracked/visible-untracked source plus the bound Git metadata. Never remove or bypass that interlock. Read-only Git remains allowed, and a different registered worktree remains independent.
- Project scripts and the launcher perform no operating-system servicing — no DISM, no Windows-feature enable/disable, no WSL install or uninstall — and must not fail closed on transient OS-servicing state. Host administration is the operator's concern, outside the build/test loop.
- The launcher builds the pinned Cppcheck 2.20.0 source commit with its matching GNU compiler and retains only the active launcher-managed Cppcheck cache root.
- Both parent code trees are owned first-class source (owner directive 2026-07-12; EPIC #286): edit them directly with the normal quality bar. The legacy overlay + pin machinery was dismantled under #286; do not reintroduce it. `patches/cbm/` is not overlay machinery — it is Astrolabe-owned libcbm build glue compiled directly by `cbm-sys/build.rs`.
- **No CI/CD (banned, owner directive 2026-07-11):** GitHub Actions and all hosted CI/CD are banned. Never create `.github/` content, cite a CI job as coverage owner, or defer evidence "until CI runs." All verification is local full-state verification, recorded on the issue.
- Keep repository-controlled outputs inside the workspace, normally in `target/`.
- Make the exact live launcher owner perform `C:\code\Astrolabe\target` cleanup after every build/verification batch, including failure or interruption, and independently verify absence before any pause, stop, issue close, turn end, or handoff. Never delete it manually on the strength of a numeric PID or a path check. If launcher protocol state is non-absent or attributed-child state prevents exact-owner cleanup, preserve `target/`, record the blocker, and complete the tracker-bound reclaim/ownership procedure before cleanup.
- Native binaries used after Cargo cleanup must be promoted before cleanup with `scripts\native-fsv-artifact.ps1 -Operation Stage`, then executed only through `scripts\native-fsv-run.ps1` while the same issue-owned launcher lease remains live. The staged receipt/tree/artifact hashes and run record are the source of truth; inspect them independently, then use `-Operation Cleanup` only after every recorded owner PID is dead. A pristine staged session that never ran is removed only with `-Operation Abandon`, after it persists an external hash-bound abandonment record and proves every receipt owner dead. A terminal partial run whose runner could not publish a valid run record is removed only with `-Operation Quarantine`: it requires the exact bound live-state and expected run-record paths, proves every receipt/live-state owner dead and both locks absent, inventories and hashes every ordinary session file into an external append-only recovery record, then removes only that session. Valid completed runs remain Cleanup-only; pristine sessions remain Abandon-only. Never execute closure FSV directly from disposable `target/`.
- **FSV-only verification (owner directive, 2026-07-13; supersedes the 2026-07-12 tiered-gate and test-doctrine directives):** the gate/check suite, gate configs, suite-impact machinery, and gate self-tests are retired and deleted — do not rebuild them. Verification is Full State Verification against reality: build the real artifact natively, exercise the real behavior with real data (never mocks), independently read back the persisted state, probe the relevant edge cases, and record command + context + readback on the driving issue. **Manual FSV only — no tests (owner directive, 2026-07-14):** all test code was deleted from the repo (`#[cfg(test)]`, `tests/` dirs, the cbm C suite, trybuild, test scripts); passing tests prove nothing. Never write, run, or cite a test for verification, evidence, measurement, or closure. Verify by exercising the real artifact yourself against a real codebase and reading back persisted state by hand; measurements run against the real binary/server. `cargo check`/`cargo build` remain valid buildability evidence.
