# Astrolabe Agent Context

`CLAUDE.md` is the repository operating manual and must be read before doing any work. GitHub issues are the state of record.

The execution boundary is non-negotiable:

- Work only from the canonical checkout at `C:\code\Astrolabe`.
- Produce build/test evidence with native Windows processes and the native GNU toolchain, because the Rust host and the static `libcbm.a` archive must share one ABI. Run POSIX scripts under a Git for Windows Bash executable (e.g. `C:\Program Files\Git\bin\bash.exe`) for a consistent, pinned toolchain.
- WSL coexistence: WSL is a normal, permitted part of this Windows machine. Project scripts, the launcher, and gates must never treat WSL (services, packages, distributions, `wsl.exe`, `wslservice`, `vmmemWSL`, `C:\Windows\System32\bash.exe`) as a fault condition, must never fail closed on its presence, and must never stop, disable, uninstall, or DISM-service it. Do not build anything that wipes or polices WSL to keep the host "pure." Evidence runs natively only to match the shipping target, not out of hostility toward WSL.
- Native evidence requirement: a build for a different target (including a Linux or WSL build) exercises different code paths and does not satisfy a Windows DoD; re-run required evidence natively and record the Windows execution context in the issue. A gate that genuinely cannot run natively is a coverage gap to file, not a host to modify.
- Run native Cargo, C build, and aggregate commands through `scripts\\windows-gnu-toolchain.ps1`; it pins the matching GNU runtime and LLVM analysis tools, confines temporary files to a launcher-owned workspace child, and removes that child and `target/` on exit. It also holds a fail-closed session lock at `.tmp/astrolabe-launcher.lock`: a session may clean `target/` or stop toolchain processes only when that lock is absent or names a dead PID; never stop or clean another session's live locked run.
- Multi-session lock discipline (#197): every lock file names owner PID(s) + issue + start time as JSON; a lock naming any live PID is inviolable (never remove it, stop its processes, or clean `target/` under it); dead-PID-only locks are cleaned only after posting PID-probe evidence to the owning issue; tracker-comment before acquiring or removing any lock and re-read the driving issue first; launch multi-hour gate runs detached from tool-call timeouts with the launcher PID posted to the driving issue at start; FSV of lock semantics uses isolated fixture roots, never the live shared workspace.
- Project scripts and the launcher perform no operating-system servicing — no DISM, no Windows-feature enable/disable, no WSL install or uninstall — and must not fail closed on transient OS-servicing state. Host administration is the operator's concern, outside the build/test loop.
- Invoke aggregate gates through `scripts\\invoke-native-aggregate.ps1` and consume its stdout directly. The wrapper intentionally creates no evidence log; never wrap it in `Tee-Object`, a transcript, or host-side redirection to any file inside or outside the workspace.
- The launcher builds the pinned Cppcheck 2.20.0 source commit with its matching GNU compiler and retains only the active launcher-managed Cppcheck cache root.
- Both parent code trees are owned first-class source (owner directive 2026-07-12; EPIC #286): edit them directly with the normal quality bar. The legacy `patches/` overlay + pin machinery is being dismantled under #286 — add nothing to it.
- **No CI/CD (banned, owner directive 2026-07-11):** GitHub Actions and all hosted CI/CD are banned. Never create `.github/` content, cite a CI job as coverage owner, or defer evidence "until CI runs." All verification is local full-state verification, recorded on the issue. The `ci/` directory is local gate config only (historical name; see #224).
- On non-Linux hosts, blocking Cppcheck targets `unix64` and emits `INFO[ASTRO_CBM_CPPCHECK_LINUX_ABI]` for a stable analyzer ABI; native runtime suites still own Windows behavior.
- On non-Linux native aggregates, `SKIP[ASTRO_CBM_CLANG_TIDY_LINUX_REQUIRED]` is a recorded coverage gap (tracked in #224 / #166–#170), not local analyzer-pass evidence. The other CBM lint gates still run.
- Keep repository-controlled outputs inside the workspace, normally in `target/`.
- Delete `C:\code\Astrolabe\target` after every build/test/check batch, including failure or interruption, and verify it is absent before any pause, stop, issue close, turn end, or handoff.
- `scripts/check-full.sh` bounds its workspace-test phase by default and exits `125` with a `DEFERRED[...]` continuation when the deadline is reached; that is incomplete evidence, never a passing aggregate. Use its printed continuation with `ASTROLABE_WORKSPACE_TEST_TIMEOUT_SECS=0` only when a full, unbounded native run is intentional.
- **Fast feedback loops (owner directive, 2026-07-12; #262):** optimize for the least wall-clock that still proves a change. Match the gate to blast radius — Tier 0 (`cargo check`/`clippy`/`nextest` on the touched crate(s), warm `target/`) for the inner loop; Tier 1 (the affected crates' suites + fmt + lint) pre-commit; Tier 2 (the full native aggregate, ~30–60 min) **only** before merging to `main` or when blast radius includes foundational surface (identity spine `astrolabe-domain`, FFI/libcbm `cbm-sys`/`astrolabe-bridge`, gate scripts, cross-crate contracts, the C half). Measure blast radius with codebase-memory-mcp `trace_path`+`detect_changes` and run the minimum covering tier — never the aggregate for a change a targeted check fully covers. Keep `target/` warm within a session's inner loop (the "contiguous verification batch" carve-out); the mandatory wipe is at every boundary (turn/pause/stop/handoff) and before release-artifact gates, and the #197 live-PID lock stays inviolable. This never weakens HONEST/FSV: closure evidence must still cover the real blast radius and label every skip.
- Make and execute the technical, environment/toolchain, prioritization, and implementation decisions needed to reach ASTROLABE's intended end state. Prefer the most robust, durable, project-aligned solution over a locally easier workaround; do not pause for routine choices or leave known next steps undecided.
- GitHub issues and their comments are the durable state record. At every resume or context compaction, re-read this file, `CLAUDE.md`, the active issue and its comments, and the current Git/worktree state before acting. A claimed or `status:in-progress` issue is still available to this sole agent.
- Treat a result as real only after direct state verification of the actual artifact, process, browser state, or persisted data. Record that evidence in the issue before closing it; commit and push the verified repository state after every issue close.
- Use the already-open authenticated Chrome session through Synapse for browser work, opening only background tabs in that browser. Keep worktrees, branches, temporary tools, and outputs clean; create and track a GitHub issue for every discovered problem that is outside the current fix.
- For the complete Rust formatter, run `python scripts/native-cargo-fmt.py --all -- --check`. Do not run bare `cargo fmt --all` on native Windows: upstream cargo-fmt submits the Calyx graph as one Windows-overlimit process.
- `vendor/calyx` and `vendor/codebase-memory-mcp` are ASTROLABE's own code, not upstream sources (EPIC #286; the `vendor/` names are historical and slated for relocation). No pins, no patch flow, no upstream tracking. Sibling checkouts (`C:\code\Calyx`, `C:\code\Calyx-Dev`, ...) are never workspaces — read-only quarries at most.
